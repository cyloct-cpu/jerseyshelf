# WhatsApp 接口与下单联系接入计划

日期：2026-10-16（Asia/Shanghai）。状态：本地代码、后台页面、前台入口及隔离测试已实施，使用方法见[WhatsApp使用说明](WhatsApp使用说明.md)。已保存用户提供的本店号码并启用点击联系，官方凭据尚未填写；未注册平台账号、未发送真实消息、未部署公网服务。以下保留原审批计划，具体边界以使用说明为准。

## 一、目标与现状

目标覆盖两个方向：顾客在网站咨询或下单后，直接联系本店；商家在后台看到新订单后，直接联系对应顾客。需要自动联系时，再通过官方 WhatsApp Business Platform Cloud API 发消息、接收回复和更新状态。

当前已有客户档案、注册/收货资料自动同步、订单关联、新订单首次联系任务、回访售后和后台 `wa.me` 聊天链接。缺少统一的商家号码设置、前台全站入口、订单消息预填、正式发送接口、消息队列和回调。

用户截图中的 `api.whatsapp.com/send` 是点击聊天跳转，并不是已配置 Cloud API 的证明。截图号码仅作为参考，不默认作为本店号码，不从参考站复制商家身份。

## 二、两种模式共用一套后台

| 模式 | 实际功能 | 依赖与边界 |
| --- | --- | --- |
| 点击联系 | 打开 WhatsApp App / Web，并预填商品或订单消息；由顾客/商家点击发送 | 本店实际号码即可配置，不请求 Cloud API；点击不能被记录成发送成功 |
| 官方 API | 网站服务器发订单消息、接收客户回复与消息状态 | 需要可用的官方业务账号/号码、对应凭据、模板及公网 HTTPS 回调；按官方现行政策和价格运行 |

建议第一阶段先把点击联系、订单消息和现有客户跟进连起来；第二阶段完成 Cloud API 适配、队列和回调，本地用隔离测试验证，实际账号和公网地址准备好后做正式联调。后台模式为关闭、点击联系、官方API，未配置完整时不声称已经连通。

## 三、前台入口

1. 全站增加 WhatsApp 浮动客服按钮，手机与桌面响应式，位置不遮挡购物车或购买按钮。
2. 商品页增加“WhatsApp咨询”，预填公开商品标题、SKU/尺码、数量及顾客已选择的定制需求；发送动作由顾客确认。
3. 购物车增加“WhatsApp确认订单”，带清单摘要，长清单避免塞进长链接。没有正式订单时不能伪造订单号；只发需求摘要或采用独立咨询编号。
4. 订单成功页增加“联系商家确认订单”，自动带订单号、商品/规格/件数及订单冻结币种和金额，不使用当天汇率重算。
5. 不强制弹出或强制跳转 WhatsApp；创建订单成功后保留网站订单页，顾客自行点击联系。

客户侧预填示例：

```text
Hello, I would like to confirm order BW-EXAMPLE.
Item: Bayern Munich Away Kit
Size: L | Quantity: 2
Order total: USD 40.00
Please confirm payment and delivery arrangements.
```

示例内容仅用于说明，不代表真实订单。预填提示语跟随当前语言，客户姓名/印字等原文不自动送外部翻译。默认不把完整地址、邮箱、支付凭证或订单访问令牌写入 WhatsApp URL。

## 四、后台联系客户

客户列表、客户详情、订单详情和“新订单待联系”都提供同一套操作：

- 从已关联客户及订单自动获取号码、称呼、订单号及商品摘要，不再手填。
- 确认接收号码及消息预览，可编辑当前消息；保存模板用于下次联系。
- 点击联系模式打开 App/Web；事件只记“打开聊天入口”，实际联系由商家记录。
- API 模式显示“发送给此客户”，通过服务器发送，列出实际发送结果；尚未取得允许联系记录或配置不完整时不自动发送。
- 缺少 WhatsApp 号码时明确显示缺号码，提供已有邮箱联系入口；不能把普通国内手机格式猜成国际 WhatsApp 号码。
- 多笔订单默认关联最近订单，可切换，服务端再次验证客户归属，不能凭前端传来的任意号码或订单号转发内容。

商家侧预填示例：

```text
Hello, we received your order BW-EXAMPLE.
Could you confirm the selected size and printing details?
We will arrange shipping after payment is confirmed.
```

## 五、下单后的消息与任务

下单成功 → 保存订单及客户/收货快照 → 建立首次联系任务 → 按配置生成待发送消息 → 客户沟通 → 核实收款 → 发货 → 回访。

- 点击联系模式：后台提醒并提供一键联系，由商家发送。
- API 模式：客户同意接收相应订单联系、有效号码、模板及账号条件满足后，才允许按开关自动发送第一条订单确认消息。
- 后续可分别开关付款跟进、发货通知和售后消息；首版默认不开启自动营销、群发或自动付款催促。
- 测试订单不触发真实发送；连通测试使用专门指定的测试收件人，真实发信必须在明确的测试发送操作中确认。
- 消息失败不回滚或删除已创建订单，不把失败记录为已联系；待办持续保留并支持改用其他渠道。
- 沟通、消息已读和收款状态独立，只有实际付款核实才能改变成交状态。

## 六、Cloud API 接入内容

后台提供独立设置页，计划收集商家显示号码、WhatsApp Business Account ID、Phone Number ID、Access Token、App Secret、Webhook Verify Token，以及选用的已批准模板名/语言。实际字段、权限和 Graph API 版本在实施时依官方当前文档核对并固定版本，不自动升级。

配置只保存在服务端，凭据加密存储，前端不回显，不写入普通日志。状态页区分“已填配置”“凭据/账号检查通过”“Webhook已验证”“指定消息真实发送成功”，不会以仅填写密钥代替实际连通证明。

官方消息策略在2026-10-16核对：商家主动发起联系使用已批准模板；客户发来消息后开启并刷新24小时服务窗口，窗口外仍需模板。消息费用以官方实时价格和业务账号账单为准，不承诺全免费。相关来源见文末。

保留客户提供号码及同意接收相应业务消息的记录，订阅营销与订单联系分开；注册、填写普通收货电话或浏览网站，不自动等于允许 WhatsApp 主动联系。号码变化时重新核对联系许可，客户退订该渠道后停止对应发送。

收到经验证的客户入站消息时，关联号码/咨询编号和客户记录，可记录实际建立联系；需要对应具体订单且有多笔候选时提示人工选择。不因为收到一个订单编号就授予网站订单查看权限，也不承诺导入个人账号全部旧聊天历史。

## 七、消息记录、队列与回调

消息记录分别展示：排队、已提交平台、平台确认发送、送达、已读、失败及待核实。平台没有提供的回执不推断；业务上“API返回接受”“消息送达”“客户已回复”“客户已成交”必须分开。

采用可靠队列及事件去重：

- 下单事件与待发送任务可靠保存，网络发送放在订单事务完成后，不阻塞结账。
- 以订单/事件/接收人/模板版本等组成去重键，刷新和重复提交不重复排队。
- 发送超时但可能已被平台接受的情况先标“待核实”，不盲目重发，也不承诺无法证明的严格一次投递。
- Webhook 验证签名、按事件标识去重，持久保存后确认接收；乱序回执不把已读倒退为发送中。
- Webhook 仅免除本地会话/CSRF要求，不能免除平台签名认证；普通后台接口的会话、管理员权限及CSRF保持。
- API不可用或额度/权限不满足时保留错误原因与待办，提供人工点击联系，不自动购买资源或切换非官方服务。

## 八、拟定接口与文件规划

接口名称是实施建议，实际按现有服务器结构调整：

| 接口 | 用途与权限 |
| --- | --- |
| `POST /contact/whatsapp` | 普通店铺/商品咨询，固定本店号码，校验CSRF、来源及频率，不接受任意目标地址 |
| `POST /orders/:id/whatsapp` | 顾客联系商家，仅当前账户/会话有权读取该订单时生成私有订单摘要 |
| `POST /admin/customers/:id/whatsapp` | 后台联系指定客户，管理员、CSRF及订单归属校验 |
| `POST /admin/whatsapp/messages` | API消息预览确认后发送，接收人和模板服务器校验 |
| `GET/POST /webhooks/whatsapp` | 平台回调验证与已认证事件接收，不作为可匿名发送消息的接口 |
| `GET /admin/whatsapp` | 号码、模式、模板、凭据状态和连接设置 |

```text
apps/api/whatsapp.mjs                      模式、消息构建、客户/订单关联
apps/api/whatsapp-provider.mjs             官方API适配与受控网络请求
apps/api/whatsapp-queue.mjs                发送队列、去重、重试和状态
apps/api/whatsapp-webhook.mjs              验证、入站消息及回执处理
apps/admin/whatsapp.mjs                   设置、模板和消息记录
apps/storefront/whatsapp.mjs              浮动入口、商品/订单联系按钮
packages/contracts/whatsapp.mjs           号码、模板参数和状态校验
database/migrations/<下一空闲版本>-whatsapp.sql
tests/whatsapp.test.mjs                    业务、权限、模拟平台与真实测试隔离
docs/WhatsApp使用说明.md                  实施后维护说明
```

数据库新增配置/加密凭据、模板、消息/发送任务、Webhook事件和接收许可记录，复用已有客户与订单主键。备份脚本包含新增凭据加密文件，不导出真实客户消息到公开目录。

## 九、准备资料与上线依赖

点击联系模式需要本店实际 WhatsApp 号码（含国家区号）、对外显示名称和默认联系语言，可在本地先完成。

官方 API 真实联调还需要已开通且可用的业务账号/号码、相关凭据、批准模板，以及平台能访问的 HTTPS 回调。当前没有服务器和域名，先做本地代码、配置页和模拟回调验证；公网回调与生产发送待部署条件具备后完成。使用现有手机App号码时，先核对该号码是否支持所选接入方式，不擅自迁移、注销或改变现有账号。

密钥在后台安全填写，不要求通过聊天传递。截图的参考商家号码不直接填入本店。

## 十、实施与验收顺序

1. 本店号码/模式后台设置及统一消息构建。
2. 全站浮动入口、商品咨询、购物车需求摘要和订单成功页联系按钮。
3. 后台客户/订单一键联系、消息预览及跟进记录联动。
4. 官方API适配、模板、队列、许可记录和Webhook；本地隔离测试。
5. 获得实际账号参数和公网条件后，向明确指定的测试号码做真实联调，再按开关启用生产订单消息。

验收包括：号码可配置且不是参考站号码；手机/桌面跳转正常；未下单不伪造订单号；不同币种/定制摘要准确；订单权限和物流专用查看权限不混用；缺号码/未许可不错误发送；点击不等于实际联系；重复下单/回调不重复记账或排队；发送失败不影响下单；客户资料不进入翻译队列；测试不联系真实客户。
