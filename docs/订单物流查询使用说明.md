# 订单物流查询

已完成第一阶段：客户查询入口、游客验证、包裹管理、运单纠错和外部物流查询。自动物流接口、发货邮件及邮件安全链接属于第二阶段，当前未启用。

## 客户使用

导航和页脚的“订单查询”打开 `/track`。游客输入订单号和下单邮箱，匹配后获得当前浏览器内 30 分钟的物流查询权限；不会获得完整订单、收货地址和电话的访问权限。登录客户可以从“我的订单”进入自己的物流页，下单原浏览器也保留原有的订单访问权限。

物流页显示各包裹的公司、单号、所含商品、状态和查询链接。UPS、FedEx、USPS、DHL、Royal Mail 使用预设官网入口，其余通过 17TRACK 查询。外部网站的轨迹由对方提供。本站没有抓取外部网页，也没有把“已录入运单”当作“已揽收”。

当前没有实时自动轨迹。页面会明确提示使用外部链接查询；数据库已预留服务商、同步状态、最近同步时间和去重轨迹事件，后续可接入 API。

## 后台发货与拆包

1. 在“订单管理”打开订单。正式订单须先人工核实收齐款项；测试订单使用模拟付款流程。
2. 在订单处理区填写运单并标记发货，系统创建首个包裹，默认包含订单全部商品。
3. 在下方“包裹管理”展开包裹，选择物流公司（其他公司需填写名称），核实运单和发货时间，然后保存。
4. 需要拆包时，先将第一个包裹数量改为实际装入数量，再通过“添加新包裹”分配剩余商品。数量为 0 表示该包裹不包含该商品。后台拒绝所有包裹合计超出订单数量。
5. 运单更正会记录操作人、时间及更正前后内容；更换物流公司或单号后清除旧轨迹缓存。没有删除订单或库存变更。

发货时间输入明确采用 UTC（北京时间减 8 小时）。客户侧展示发货日期。历史已发货运单自动迁移为包裹；原订单未记录发货时间的，不猜测发货日期。历史包裹默认分配全部商品。

正式订单原有“确认收货”操作同步将该订单所有包裹标记为已签收；这属于人工确认，不代表物流 API 返回结果。当前没有单独的包裹签收编辑或自动异常提醒。

## 安全与数据

查询通过 POST 提交邮箱，不放入 URL；限制同 IP 和同会话查询频率，并要求 CSRF 校验。后台包裹操作仅管理员可用。物流查询授权独立存放于 `tracking_access`，不修改原有完整订单访问权限。

新增迁移 `019-order-shipments.sql`。数据表包括 `shipments`、`shipment_items`、`shipment_events`、`shipment_changes`、`tracking_access`。常规 SQLite 备份包含这些数据。

## 下一阶段

确定实际承运商并使用真实运单验证后，接入一家服务商的 API：运单注册、推送验签与去重、重试和补查、轨迹缓存及异常显示。需要服务商账号和可用额度，以及部署后的公网 HTTPS 回调地址。本站第一阶段不需要 API 密钥，也不产生物流 API 费用；外部查询服务政策以其官网为准。

发货邮件及邮件中安全查询链接需要再配置邮件发送服务。当前不发送邮件、短信或 WhatsApp 通知。

## 验证

`node --test tests/tracking.test.mjs` 覆盖游客访问隔离、过期授权、CSRF、限流、后台鉴权、发货包裹、拆包超量和重复运单拒绝、纠错审计、旧轨迹清除及客户隐私保护。
