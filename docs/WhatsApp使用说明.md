# WhatsApp 联系与官方接口

本地实现日期：2026-10-16。入口：[WhatsApp管理](http://127.0.0.1:3001/admin/whatsapp)。已根据用户提供的本店号码（尾号4144）启用点击联系；官方凭据尚未填写，官方自动发送关闭，未部署公网回调，未发送真实消息。

## 先使用点击联系

1. 管理后台 → **WhatsApp联系**，选择“点击联系”。
2. 填入**本店实际WhatsApp号码**，包含国家区号，支持 `+`、空格及括号；保存时统一为数字。不要填参考网站的商家号码。
3. 可填写客服显示名称、后台预填消息默认语言，以及自定义订单联系模板。
4. 保存后，商城显示浮动客服入口、商品咨询、购物车咨询及订单成功页联系按钮。未配置号码时隐藏入口，避免客户跳到错误号码。
5. 客户列表、客户详情或订单详情 → 预览WhatsApp联系 → 核对号码及关联订单，可编辑消息 → 打开WhatsApp → 在App/Web中自行发送。

点击聊天模式不调用Cloud API，不需要API凭据。跳转目标仅为服务器确定的 `https://wa.me/号码`；前台不能指定任意目标号码。订单摘要只允许有完整订单查看权限的账户或游客原会话取得，物流查询权限不包含订单咨询摘要权限。

商品咨询带选择的尺码、件数、印字和臂章；购物车超过3行时仅带前3行摘要，不伪造订单号。订单咨询带订单号及冻结币种/金额，不重新计算汇率。预填链接限制1200字符，长内容可能截断，应在后台/订单页核对完整清单。不会把完整地址、邮箱、付款凭证或网站访问令牌放进链接。

后台点击只记录“打开聊天入口”，不会自动标记已发送、已联系或已成交。实际沟通请在客户档案记录结果并处理联系待办。关闭模式会隐藏前台入口并停止官方队列，后台保留原有人工联系客户的能力。

## 客户号码及订单许可

- 结账页有单独的WhatsApp号码，收货联系电话仍独立保存。
- 客户主动填写的订单WhatsApp号码会作为客户档案的自动资料来源；已手工覆盖的客户号码保持原值。后台联系该订单优先使用其WhatsApp快照。
- 许可复选框默认不勾选。勾选必须同时提供有效国际号码，许可来源和时间写入客户时间线。
- **许可对应本次订单及具体号码**。曾允许一个订单，不代表后续未勾选的新订单也可以由API主动联系。注册或填写收货电话也不等于许可。
- 客户档案显示许可记录，可撤回。官方入站消息为 `STOP`、`UNSUBSCRIBE`、`退订` 或 `停止` 时撤回此号码许可并取消尚未提交的排队消息。已提交给平台的消息不能撤回。
- “停止普通购买跟进”与明确允许的订单服务联系分开；归档客户不进入官方发送。新正式订单恢复档案仍沿用现有CRM逻辑。

## 开通官方Cloud API后

当前无服务器和域名，此部分先完成本地实现及模拟测试。准备好账号和部署条件后按顺序操作：

1. 在Meta业务平台准备可用业务号码及账号，核对号码的接入资格，**不需要为了本地代码擅自迁移或注销现有手机App账号**。
2. 在本地后台填写本店号码、WABA ID、Phone Number ID、Access Token、App Secret和自行设置的Webhook Verify Token。
3. API版本按Meta账号控制台/现行官方文档填写，代码不自动升级版本。页面的 `v24.0` 仅为格式示例。
4. 在Meta创建并批准正文文本模板，然后在后台填写完全一致的模板名、语言及参数顺序。目前支持 `order_id,name,items,total,tracking`，以英文逗号分隔；对应正文 `{{1}}`、`{{2}}` 等数字占位。暂不支持标题、页脚、按钮、媒体或命名参数模板。
5. 保存后点击“检查官方账号与模板”。它只读取号码、WABA号码归属和前100个模板，不发送消息；已批准模板才允许排队。检查24小时有效，修改账号/号码/Token/App Secret/模板后需要重查，检查失败也会清除旧通过状态。
6. 部署后在Meta填写 `https://您的域名/webhooks/whatsapp`，使用后台设置的Verify Token完成验证，并订阅该WABA的 `messages` 事件。需要确认业务应用权限和WABA订阅，不能只完成GET验证就视为已收通回调。
7. 核对官方费用、模板和明确指定的联调收件人后，再开启“实际发送”。本次交付没有启用这一开关，也没有执行真实联调。

官方发送均使用已批准模板，即使处于24小时服务窗口也不提供任意文本自动发送接口。费用以[官方价格](https://business.whatsapp.com/products/platform-pricing)和账号账单为准。

## 订单联系流程

正式订单提交 → 客户档案与原有首次联系/付款待办 → 按开关排队订单确认 → 商家沟通核实付款 → 发货 → 按开关排队发货通知 → 在订单页预览并手动提交回访或售后模板。

自动确认和自动发货通知可分别开启，默认都关闭。付款沟通、回访和售后从订单页预览模板后确认排队，不自动群发或自动催款。测试订单不能进入真实发送队列。配置缺失、许可不满足或接口失败时，订单和跟进待办保留。

订单页模板预览会显示接收人、官方模板名称/语言和实际正文。提交时服务器再次核对号码、订单和模板，预览后发生变化则要求重新预览。重复提交同一个请求不会重复排队；再次打开新预览是新的操作，应先检查历史消息。

## 回执与回复

后台区分“排队中 → 提交中 → 平台已接受 → 已发送 → 已送达 → 已读”，也显示失败、已取消和待核实。平台接受不代表已送达，消息已读不代表已付款。收款仍按既有人工核实流程处理。

- Webhook POST按原始请求体验证 `X-Hub-Signature-256`，限制256 KiB；不依赖浏览器会话或CSRF，其余普通接口仍验证管理员/订单权限、来源和CSRF。
- 按签名有效事件及平台消息ID去重；回执乱序不让已读退回已发送。先到达的回执会保存，HTTP返回消息ID后再关联。
- 回复只匹配已知号码，唯一匹配的客户才自动关联。消息带订单号时还要验证其属于该客户。没有匹配或有多个候选的消息标为“待核对客户”，请在客户档案核对号码；不凭订单号赋予账户订单访问权限。
- 主号码收到有效回复可记录已建立WhatsApp联系；历史号码仍保留消息记录，不将另一个号码误标为已核实。后续业务待办由商家核对处理。
- 首版保存文本内容，非文本消息记录类型，不下载媒体，不导入个人账号历史聊天。
- 明确HTTP429限流最多尝试3次，间隔60秒；网络超时、5xx、无消息ID等结果不确定的情况不自动重发，标为“待核实”。
- 多实例通过数据库事务认领消息；提交超过60秒仍无结果的消息转为待核实。重启不会抢走另一实例刚认领的消息。此机制避免盲目重发，不承诺无法证明的严格一次投递。

## 文件与维护

| 文件 | 职责 |
| --- | --- |
| `apps/api/whatsapp-config.mjs` | 模式、模板设置与凭据加密 |
| `apps/api/whatsapp.mjs` | 消息摘要、订单许可、排队与客户联系 |
| `apps/api/whatsapp-provider.mjs` | 固定Meta官方HTTPS接口、超时和错误分类 |
| `apps/api/whatsapp-queue.mjs` | 队列、重试、配置变化校验与重启恢复 |
| `apps/api/whatsapp-webhook.mjs` / `whatsapp-receipts.mjs` | 验证、回复、回执去重及乱序处理 |
| `apps/admin/whatsapp.mjs` | 设置、预览、许可与消息记录 |
| `apps/storefront/whatsapp.mjs` | 前台入口 |
| `database/migrations/021-whatsapp.sql` | 订单快照、许可、消息、回调及回执表 |
| `tests/whatsapp.test.mjs` / `whatsapp-http.test.mjs` | 隔离数据库及模拟平台测试 |

凭据以AES-256-GCM加密保存在数据库设置中，加密文件 `whatsapp-credentials.key` 与数据库同目录；不回显到后台表单，不写入普通日志。代码已忽略该文件，备份脚本包含它。恢复时数据库和加密文件须成套恢复，备份含个人信息与密钥，勿放入公开目录。

队列随商城服务每3秒处理一条。测试时设置 `WHATSAPP_AUTO_UPDATE=false`。此开关是进程级停止处理，后台“实际发送”是持久化业务开关。未启用官方模式时不会调用消息接口。

后台和客户消息页不进入前台自动翻译队列。提示语使用既有多语言系统；私有姓名、印字、地址和聊天正文不会提交外部翻译。Meta模板语言独立配置，不随浏览器语言自动切换到另一未经核实的模板。
