# 顾客购买体验与后台运营优化计划

日期：2026-10-17。

## 1. 依据与结论

本计划依据当前项目源码、只读数据库统计及已有使用说明制定；本轮没有开展浏览器全流程实测，没有创建订单、修改库存、触发通知或执行部署。页面视觉、移动端交互、真实物流及正式收款的表现列入后续验收，不视为已经验证。

当前关键事实：

- 商品4,166件，均上架；规格23,521条，仅7条规格启用且库存大于0，集中在1件商品。此统计是系统中的可售数据，不代表仓库实际库存。
- 当前新订单模式为货到付款（COD）；购物车、立即购买、规格与定制、优惠、游客结账已实现。
- 统一订单中心已实现：全部订单、待确认与跟进、发货与物流、代收与回款、售后处理；详情已有商品与客户、跟进、物流、资金、售后、历史分栏。
- 客户建档、任务与负责人、沟通记录、发货资料复制、CSV、包裹、人工签收/代收/回款、部分售后和退款登记已有基础能力。新计划优先改善这些入口及联动。
- 当前政策页面记录为0，站点客服邮箱、Logo为空，正式订单为0；不能据此计算真实转化率或运营效率。
- 商品通用描述仍承诺全球配送、付款后24–48小时发货及30天退款；需要与COD、实际配送范围及人工审核规则逐条统一。
- 本站物流以人工登记和外部查件链接为主；后台登记退款不等于自动转账。通知、正式物流及回款需要分别实测。

优先顺序：真实可售和经营承诺 → 手机购买路径 → 后台每日处理效率 → 自动化及增长。

## 2. 顾客身份：从进入网站到完成售后

| 环节 | 优化内容 | 验收标准 | 优先级 |
|---|---|---|---|
| 首次访问 | 首屏交代商品定位、实际配送市场、COD条件、客服；优先展示真实可售商品，导航聚焦球队/国家队/赛季/类型 | 手机首屏能辨认卖什么、如何找商品、如何联系；主推入口有可售商品 | P0/P1 |
| 找商品 | 保留已有别名搜索，增加球队、赛季、成人/儿童、球迷/球员版及可售筛选；筛选后保留条件；无结果给清除筛选与相关分类 | 搜索词与结果相关，手机筛选可关闭，返回列表条件保留 | P1 |
| 看商品 | 图片、完整价格、可选规格、库存、尺码表、材质、定制规则、配送时效、售后摘要靠近购买区 | 首批每件商品必填资料齐全；无可售规格不能进入可提交订单 | P0/P1 |
| 尺码定制 | 尺码表按款型展示厘米/英寸及测量方法；印字、号码、臂章费用逐项更新；展示最终文字和选项确认 | 商品页、购物车、结账、订单及后台定制快照一致；不误称文字确认是实物效果预览 | P1 |
| 手机操作 | 图片比例固定，操作按钮易触达；按实际页面决定底部固定购买栏，避免遮住内容；处理加载、失败、缺货提示 | 360/390/768/1440像素无关键遮挡或横向溢出；键盘打开后可操作表单 | P1 |
| 购物车 | 显示尺码、印字、臂章、定制费和优惠；提示距离免邮的件数；明确修改定制的入口 | 加减数量、删商品、刷新、后退均保留正确信息；优惠门槛前后金额一致 | P1 |
| 结账 | 保留游客下单；按国家动态显示地址字段；先核实可配送、可COD和运费；明确实际代收币种与金额；WhatsApp联系选项说明清楚 | 不支持的配送组合不能提交；错误定位字段且保留输入；同一请求不生成重复订单 | P0 |
| 下单成功 | 显示订单号、金额、定制、收货资料和下一步；COD写明待确认、无需在线付款；查询入口和客服可直接使用 | 顾客可复制订单号、重新查询；刷新成功页不重复创建订单 | P1 |
| 订单后续 | 账户与游客查询提供一致的待确认、备货、已发货、运输异常、签收信息；注明人工更新和外部轨迹查询边界 | 查询只能访问获授权订单；不把签收标成已回款；多包裹分别显示 | P1 |
| 售后回购 | 先补清晰的售后联系入口与政策；后续增加客户自助申请、证据上传和进度查询；注册、找回密码、地址簿分期完善 | 申请关联原订单与商品，不能重复超量申请；普通客户看不到内部备注与财务凭证 | P1/P2 |

### 内容优先处理

1. 选定首批真实经营商品，逐件核对价格、规格、库存、尺码、定制和履约能力；不要批量制造库存。零库存款根据实际经营选择明确缺货、合法真实的预售规则或暂不展示购买。
2. 完成配送、COD、退换货、隐私、条款、FAQ、联系页面，页脚与结账链接均有正文。
3. 统一商品模板、页面、结账及后台配置的承诺。COD使用“资料确认后备货/发货”的真实规则，预付款使用对应付款规则，定制款注明加工时间和售后条件。
4. 已有模拟热度即使标注，也建议不放在主要成交信息区；评价与成交信息以有依据的内容展示。
5. 先验收主销市场语言。翻译任务完成不等于人工审核完成，价格、尺码、付款与售后文案必须抽查；减少无必要的语言入口。

## 3. 管理人员身份：打开后台就知道该做什么

### 3.1 首页围绕每日工作

保留已有订单待办数字，增加“只看我的任务”、负责人、截止时间、逾期时长、优先级、下一步操作和返回列表位置。订单及客户同一业务任务使用明确关联，避免一笔新订单让两个工作台重复提醒、重复联系。各待办可重叠，不能相加当订单总数。

建议默认排序：逾期异常/紧急售后 → 今日待确认 → 已确认待发货 → 已签收待核实代收 → 逾期待回款 → 常规回访。分别配置时限，不能把所有任务都设成相同时间。

### 3.2 订单列表和详情

- 列表显示订单号、下单时间、国家、件数、定制标记、订单金额/代收币种、负责人、订单/物流/资金状态、下一步和停留时间。
- 在已有搜索上补日期、国家、负责人、支付方式、承运商、定制订单、异常类型筛选；保存常用视图。
- 将状态拆为客户确认、履约、资金及售后，允许同时存在。例如“已签收 + 物流商待回款 + 部分退款处理中”。
- 详情继续使用现有分栏，增加固定摘要和按状态给出的主要操作；修改收件信息保留原始订单快照、核实依据及历史。
- 备货输出拣货清单和定制制作单，明确每件尺码、姓名、号码、臂章、数量及包裹归属。定制进入制作前记录确认依据。
- 对现有复制、导出、单号回填补适配真实物流模板、导入预检、逐行错误和重复单号检查。
- 批量操作先做分配负责人、导出、待办处理和物流导入；逐单校验、展示成功/失败结果。退款、核实代收及回款仍需明确金额、依据和权限。

### 3.3 客户、商品及库存

客户详情串联已有档案、订单、联系许可、任务和沟通历史；修改号码不覆盖过去订单；打开聊天不自动算联系成功。同一客户多个订单保留独立待办，退订客户不进入普通营销任务。

商品列表增加“有库存可售、上架无可售规格、资料缺项、翻译待审、库存不足”等视图及批量编辑。把上架与可购买分开显示。库存预警落实到SKU；记录预占、可用、制作/出库及退货验收的变化，取消与退货不能重复恢复库存。COD未确认订单采用跟进与有依据的释放规则，不套用预付款未支付自动取消。

### 3.4 资金与售后

保留现有多币种、退款抵扣和差额处理能力，增加承运商对账单导入及匹配结果、未匹配订单、少款、多扣、跨币种差异和账龄分组。财务页面分开显示客户应付、实际代收、物流扣费、实际回款、退款、未结差额；多币种分币种汇总，换算报表展示汇率和时点。

增加可售退回、损坏、拒收、换货、补发的操作提示，所有资金或库存变化能追溯到原订单、商品、凭证和操作人。退款登记明确是人工转款后的记账。

### 3.5 多人协作与权限

当前代码主要区分管理员和客户。若由多人经营，在正式多人使用前增加店主、客服、仓库、财务权限：客服不调整资金，仓库不登记回款，财务不修改商品定制。限制客户导出和查看敏感资料，记录角色/权限变更。负责人分配、日志查看和高影响操作校验同步验收。

### 每日标准操作

1. 客服处理今日与逾期确认，核实地址、电话、定制、COD金额与币种，记录结果及下次联系。
2. 仓库处理已确认可发货订单，按拣货/定制单制作检查，导出物流资料并回填运单。
3. 客服处理运输异常、拒收、地址问题和售后，明确负责人和截止时间。
4. 财务按凭证核实代收与回款，处理差额与退款，不以签收推断到账。
5. 店主查看遗漏待办、低库存、未匹配账单和备份/通知失败情况。

## 4. 先验收、再按问题落实

### 实测范围

在独立测试数据库完成写操作；现有运营库只读，不创建假正式订单。

- 顾客路径：手机与桌面，游客与注册用户，普通款与印字/臂章款，购物车购买与立即购买，中文与主销语言，默认币种与目标代收币种。
- 边界：最后一件库存、超库存、商品下架、定制调整、错误地址、不可配送地区、报价过期、重复点击、双标签页、网络中断、切换语言、刷新后退。
- 商家路径：确认、取消、拣货、拆包发货、物流更正、异常、拒收、部分退货、损坏验收、换货补发、分次退款、部分回款和跨币种差额。
- 权限：未登录后台、跨账户订单、游客查询、私有证据访问、不同岗位操作、客户导出。

每项记录复现步骤、设备/语言、预期、实际、证据、严重度、负责人和复测结论。自动测试与浏览器验收分别记录；真实物流、资金及消息再用受控试单验证。

### 验收门槛

- P0：金额、库存、重复订单、订单越权、错误资金操作；修复前暂停受影响上线流程。
- P1：主购买路径中断、移动端无法操作、定制丢失、不可履行的经营承诺、关键管理任务无法完成；试运营前解决。
- P2：非阻断的筛选、排版、批量效率和体验增强；按影响安排。
- 所有首批商品都有真实可售资料；目标市场各完成至少一条成功路径，不支持地区有明确阻断。
- 所有资金/库存例外都有记录，没有重复扣减、重复恢复、超量或超额处理。
- 订单、物流、代收和回款各自可追踪；异常不会被正常状态覆盖。

## 5. 实施排期与交付

以下是工作量估算，不是固定发布日期；以当前单人开发加商家配合为假设，各阶段可根据验收调整。

| 阶段 | 工作 | 估算工作量 | 交付/退出条件 |
|---|---|---|---|
| A 基线验收 | 备份核实、隔离测试环境、双身份浏览器实测、问题分级 | 2–3个工作日 | 可复现问题表、截图、真实上线阻断项 |
| B 成交前提 | 首批商品、真实配送/COD规则、品牌客服、政策及模板统一 | 3–5个工作日，不含大规模商品录入 | 首批商品真实可售，费用/币种/时效一致 |
| C 前台购买 | 搜索筛选、详情/尺码/定制、手机操作、结账及成功页 | 4–7个工作日 | 手机和桌面端完整购买路径通过 |
| D 后台效率 | 我的任务、筛选、统一提醒、制作/拣货单、商品批量维护、岗位权限 | 4–7个工作日 | 同一订单可从待办一路处理，信息不重复录入 |
| E 自动化 | 真实物流模板/接口、通知、对账导入和异常队列 | 5–10个工作日，取决于外部资料和账号 | 成功、失败、重试、重复推送均有验证结果 |
| F 上线验收 | 目标环境性能、HTTPS、权限、备份恢复、受控真实订单、回滚预案 | 3–5个工作日 | 关键缺陷关闭，恢复和真实履约验证通过 |

总量约21–37个工作日；不含等待资质、账号、物流接口、素材及大批量运营资料的时间。可先完成A–D，手工物流闭环充分验收后小规模试运营，再逐步替换为自动接口。正式发布仍按既有安排另行确定；本计划不执行部署。

## 6. 运营和性能指标

前台漏斗：商品访问 → 选规格 → 加购/立即购买 → 开始结账 → 提交订单 → 确认 → 发货 → 签收 → 实际代收 → 回款。购物车路径与立即购买路径分开统计；COD下单不算已收款转化。测试订单、内部操作及重复事件排除。

后台指标：首次联系等待时间、确认到发货时间、每单处理时间、逾期待办、签收/拒收率、待回款账龄、对账差异率、售后首次响应和解决时长。比例明确分母、时间窗及订单归属，未到履约时间的订单不混入拒收判断。

先记录试运营基线，再设改进目标；当前无正式订单，不承诺转化率增长幅度。可先以单笔订单演练5分钟内完成核对和物流资料导出、无重复录入和漏填作为内部效率目标，真实流程后调整。

公网性能目标：真实访问第75百分位LCP≤2.5秒、INP≤200毫秒、CLS≤0.1；上线前用实验室和限速场景检查，上线后以真实访问补齐评价。优先首屏图片、尺寸稳定、列表缩略图、缓存与图片加载顺序；不以本地截图或一次测速声称公网通过。

## 7. 商家资料与技术依赖

第一批必须确定：首批销售商品与真实库存、主销国家和语言、物流商可配送/COD范围、实际代收币种/费率、品牌Logo与客服、备货/定制时效及售后规则。技术侧可在等待资料时先做隔离验收、问题记录、工作台布局及导入模板预检。

第二批：真实物流下单/对账模板和接口文档、邮件及WhatsApp账号配置；密钥仅通过配置渠道填写，不写在计划和截图里。

正式上线：域名、服务器、持久存储与备份位置、发布窗口及负责人员；先验证恢复，再讨论扩容或数据库迁移。
