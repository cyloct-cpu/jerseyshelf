# 多店铺统一上架与本地图片同步计划

日期：2026-10-18。本轮仅制定计划，不修改业务功能或执行发布。

## 目标与默认方案

朋友圈图片下载到电脑后，只整理一次商品资料，在一个后台选择目标店铺批量发布；后续换图、改价、下架能够选择同步范围，并看到各店铺结果。

默认后续店铺继续使用本项目系统，采用一个管理后台、统一商品库、多个店铺前台。每个店铺可以绑定自己的域名、品牌、语言、币种、价格、商品范围和经营设置。多个域名如果只指向同一个店铺，只是增加访问入口，不等于多个独立店铺。

若后续包含其他平台的店铺，保留连接器扩展：统一商品库向各平台发布，通过官方授权接口对接；平台能力和限制在确定平台后核实，不预先承诺所有平台都能同样同步。

## 现有基础与缺口

- 已有商品、规格、分类、媒体库、批量JSON导入及预检。
- 图片按内容哈希去重，可复用现有媒体保存逻辑；相同文件换名可去重，裁剪或压缩后的相似图片需另外提示。
- 现有导入要求先提供商品结构和媒体库路径，不能直接把一个普通图片文件夹变成完整商品。
- 目前数据结构以单店铺为主，缺少店铺归属、商品发布映射、同步任务和分店覆盖规则。不能只新增域名配置就当作完成多店铺。

## 日常使用流程

朋友圈保存图片 → 按商品分文件夹 → 后台选择文件夹或ZIP上传 → 系统分组生成草稿 → 补齐商品资料与检查主图 → 选择店铺和价格 → 预览 → 一键发布 → 查看逐店结果。

建议目录示例：

```text
待上架/
  SP0001-阿根廷主场球衣/
    01-主图.jpg
    02-背面.jpg
    03-细节.jpg
    04-尺码表.jpg
  SP0002-巴西训练服/
    01-主图.jpg
    02-细节.jpg
```

一个子文件夹对应一个商品，文件夹名可辅助生成名称。系统允许调整分组、拖动图片顺序和指定主图。尺码表单独标记，避免当成主图。

图片不足以可靠确定价格、库存、尺码及定制规则。这些信息需要填写、选择模板或通过配套表格导入；未知库存保持不可售。散图先进入待整理区，不直接自动上架。

## 第一阶段：本地图片批量建品

1. 新增“图片批量建品”入口，保留原JSON导入工具。
2. 支持选择文件夹及ZIP导入，保留目录分组；校验实际图片类型、文件大小、压缩包展开大小及安全路径。
3. 展示分组缩略图、主图选择、图片排序、重复文件提示及失败明细。
4. 支持批量设置分类、赛季、基础价格、尺码模板和定制模板；单件可修改。
5. 导入生成草稿。缺少必填资料、有效规格或可售库存时禁止正式发布。
6. 使用导入批次和商品编码识别重复提交；跨商品共用的图片允许复用，图片相同不直接判定商品相同。

验收：用一批真实下载图片验证商品分组、顺序和草稿；同一批重复导入不重复建品；失败文件可单独重传；不更改现有商品。

## 第二阶段：统一商品库与多店铺发布

新增店铺管理及商品在店铺的发布记录。商品用稳定的内部商品ID关联，各规格使用稳定SKU，不依赖商品名称、图片名或网址标识做长期匹配。

共享信息：商品编码、基础图片、基础描述、规格和定制资料。

可按店铺覆盖：标题与翻译、售价和币种、分类、网址标识、商品排序、主图与图库选择、上下架状态。店铺品牌、客服、政策、配送及COD配置分别维护。

后台提供“发布到店铺”面板，可勾选多个店铺，预览缺失字段、分类对应和价格后发布。商品列表显示各店铺的草稿、已上架、待更新或失败状态。

默认仅同步勾选的字段。店铺单独改过的价格、文案及图片选择受到保护；覆盖前给出差异预览，明确选择后才覆盖。修改基础商品先标记待更新，初期不默认自动覆盖所有店铺。

对于同系统店铺，可通过统一商品库和店铺发布记录提供数据，不必为每个域名复制一套商品和图片。独立平台则通过发布任务和目标商品ID维护映射。

验收：同一商品一次发布到两个测试店铺；两店可设置不同价格和分类；修改后可只更新其中一家；重试不重复创建商品；一家下架不影响另一家。

## 第三阶段：文件夹自动同步

先完成手动批量导入，再增加运行在下载电脑上的同步助手。服务器无法直接读取用户电脑上的磁盘路径，浏览器上传也不承担无人值守的长期目录监控。

同步助手只监控用户指定的目录：检测文件写入完成后上传，记录上传进度、文件标识和批次；断网后续传，重复文件跳过，认证凭据可撤销。

自动同步默认只更新待整理素材或草稿。新文件不自动变成在售商品，电脑删除原图也不触发线上删除或下架；现有商品换图先进入待确认更新。电脑关机期间暂停同步，恢复运行后补传。

验收：连续保存图片时不上传半成品；断网恢复后可以续传；重命名不重复上传相同文件；删除本地文件不破坏线上商品。

## 第四阶段：多店库存与运营隔离

如多店销售同一批货，使用一个库存来源统一预占和扣减。需要处理并发下单、取消释放、COD未确认订单占用、拒收及退货验收入库。独立平台存在同步延迟时，需要配额或安全库存，不能把定时复制库存视为实时防超卖。

如果各店货源独立，按仓库或店铺维护库存池，不强行共享库存。

订单保留来源店铺、下单时品牌/币种/价格快照。客户登录、会话、权限、订阅和联系授权明确店铺范围；一家店的营销授权不默认适用于其他店铺。

在第二家店开始真实销售前完成本阶段必要的库存及数据隔离，不推迟到超卖后再处理。

## 发布可靠性与图片管理

- 每次发布记录商品版本、目标店铺、字段范围、操作人和逐店结果。
- 同一商品对同一家店的任务按版本顺序处理，旧任务不能覆盖新版本。
- 失败只重试失败项；完成的店铺不重复建品。提供上次成功版本和恢复途径，恢复不覆盖后续订单与库存流水。
- 图片导入后存到服务器管理的媒体库，电脑路径只作为来源记录。线上不依赖电脑开机。
- 共享媒体按引用管理：删商品不立即删所有共用图片；无引用媒体经保留期和确认再清理。
- 后续需要时支持集中图片存储和分发，按部署规模确定，不在当前计划中选购服务。

## 推荐实施顺序

先做第一阶段，让现有店铺真正实现“文件夹批量建品”；随后建设第二阶段，并在第二家店真实销售前落实第四阶段必要能力；最后增加第三阶段自动监控，减少人工上传。

第一批交付范围建议为：文件夹/ZIP导入、图片分组、商品草稿、模板批量填写、预检、批量上架。多店铺发布能力作为紧接着的第二批交付。

## 开发前需要确定的经营信息

1. 后续店铺是否都使用这套系统，还是包含其他平台。
2. 不同店铺销售同一批货还是独立货源；是否使用不同价格与币种。
3. 提供一份真实图片目录样例，用于确定分组方式、主图顺序及配套商品信息来源。

以上信息影响后续实施，不阻碍先设计文件夹导入与草稿流程。原隐私声明完善计划单独保留，本计划不代表已实现多店铺功能。
