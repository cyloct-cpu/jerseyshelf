# chenyikan.shop 复刻实施方案

分析日期：2026-10-13（Asia/Shanghai）。本文件是实施规划，不代表前台、后台或全站资源已完成。

执行补充：已实现可运行的本地商城/中文后台基础版本，实际技术调整为 Node HTTP + 服务端模板 + SQLite，原因是原站及 npm 下载不可达。14 件首页商品、31 个分类已初始化，原图与全量采集仍未完成。当前实际状态和限制以《阶段验收记录.md》和《本地使用说明.md》为准；本文件下方保留原始目标规划，不应当作完成清单。第 8 步按用户要求暂不执行。

## 1. 已检查的内容和限制

- 已读取用户打开的首页可访问性结构；节点使用 shoplaza-section 命名，推断原站使用 Shoplazza。
- 已核对公开首页和 /collections/2026-27-season 分类页。分类页返回 812 Products；此数字是页面显示值，不是完成去重后的全站商品数。
- 首页包含轮播、两组球队分类、赛季/复古/风衣商品区、秋冬/短裤入口、博客、品牌、客户评价、文章入口、邮件订阅、政策链接和 SaleSmartly 客服。
- 存在账号登录/注册、搜索、购物车入口。分类页有筛选和排序。
- 公开页面资源链接中观察到 img.staticdj.com；图片还需逐页采集后才能统计。
- 浏览器显示中文，公开页面读取结果是英文；商品排序也不同。可能与翻译、会话、缓存或原站更新有关，原因未验证。以用户浏览器显示作为视觉基准，另存原始文案和翻译，不直接把自动翻译当作站点原生数据。
- 截图和浏览器 DOM/资源读取发生超时；命令行直连失败；商品页和购物车的网页读取未成功。颜色、尺寸、字体、SKU、定制选项、结账和支付尚未确认，不据此承诺像素一致或全站完整。

参考页面：
- https://www.chenyikan.shop/
- https://www.chenyikan.shop/collections/2026-27-season

## 2. 复刻目标

将可公开访问的页面、原图、文字、价格、分类关系和交互采集成固定快照，开发可独立运行的商城和中文管理后台，交付源码、数据、媒体文件及自有服务器部署文档。

原站后台程序、历史订单、客户资料、私有库存和第三方账号无法从前台获取。新后台重新实现；如后续提供原站合法导出数据，再设计迁移。支付、邮件及客服使用新站自己的服务配置，不沿用原站账号或将请求发送到原站。

## 3. 推荐架构（待实施时锁定版本）

默认按照 Linux 自有服务器规划。采用 TypeScript：Next.js 商城和独立管理界面，NestJS API，PostgreSQL 数据库，数据库迁移工具。以模块化单体组织业务，避免早期拆成大量服务。

- 商城：页面服务端渲染、产品详情、分类、搜索、购物车、订单和 SEO。
- 后台：中文界面，运营人员通过表单管理商品、图片、首页模块和订单。
- API：唯一业务入口，服务端计算金额、验证权限及处理库存和订单状态。
- 媒体：本地持久化目录起步，通过统一存储接口提供访问；以后可迁移到 S3 兼容对象存储。
- 部署：Docker Compose + Nginx + HTTPS。数据库不公开到互联网。
- 队列/Redis：仅当导入量、邮件重试或并发要求确有需要时引入，不作为基础依赖。

本轮未安装依赖。实施时核对框架官方文档、版本兼容性并生成锁文件。

以上是目标目录；本轮只创建 docs、data/source、data/manifests。运行数据、图片、备份、密码与生成文件不混进业务代码。正式媒体访问使用 media ID，不让商品直接依赖硬编码绝对磁盘路径。

## 5. 详细实施顺序

### 第一步：建立页面清单及视觉基准

1. 固定浏览器语言、币种和桌面/手机视口。
2. 保存首页完整截图、菜单展开、轮播各帧、页脚和浮层截图。
3. 从导航及公开站点地图（如存在）建立分类、商品、文章和政策 URL 清单。
4. 抽样检查普通球衣、儿童款、复古款、外套等商品，记录规格和交互差异。
5. 检查分类分页、筛选、排序、搜索、账号、购物车和结账；不在原站创建真实订单。
6. 生成页面类型矩阵，区分已检查、待检查、访问失败及未公开内容。

验收：每种页面模板和关键状态有可回看的基准；不再凭首页推测详情页。

### 第二步：完整采集资源和内容

1. 如可取得原站商品导出，优先以导出数据校验公开页面采集。
2. 遍历分类分页和产品详情，以产品稳定标识或规范 URL 去重；保留商品到多个分类的关系。
3. 记录标题、描述、slug、价格、原价、币种、SKU、规格、图片顺序、SEO、状态；未公开的字段记为未知。
4. 下载可访问的轮播、分类、商品主图/详情图、品牌、评价、文章图、图标和可用字体。
5. 解析 img/srcset、懒加载和 CSS 背景，尽量选择可获取的高分辨率文件；无法取得原图时明确记录。
6. 每个文件记录原 URL、所属页面/商品、尺寸、类型、SHA-256、保存路径、采集时间和成功/失败状态。
7. 按哈希去重，同一图片引用同一个媒体记录；保留原图，另生成缩略图和现代格式副本。
8. 内容中的远程图片链接转换为新站本地媒体引用，限制不可信 HTML，移除脚本、原站追踪及私有配置。
9. 限速、断点续传、有限次数重试；失败项进入报告，不用无关占位图冒充已复刻图片。

验收：输出唯一商品数、分类数、图片数、文件体积、失败清单；采集范围内不依赖原站图片外链。目录下现有空文件夹不代表采集完成。

### 第三步：数据库和数据导入

主要实体：Product、Variant、Collection、ProductCollection、Media、ProductMedia、Page、Article、Navigation、HomeSection、Customer、Address、Cart、Order、OrderItem、Payment、Shipment、Promotion、Subscriber、AdminUser、Role、AuditLog。

- 商品与分类多对多，SKU 单独管理库存和价格。
- 金额使用整数最小货币单位或精确数值类型，记录币种。
- 订单保存成交时名称、规格、单价、定制内容和地址快照，不受后来改价影响。
- 采集数据与正式运营数据隔离。导入支持预览、幂等更新、批次报告，默认不覆盖运营人员后续修改。
- 不把公开页面“可购买”推断成准确库存数量。

验收：样本导入正确后再全量导入，重复执行不生成重复商品。

### 第四步：前台复刻

依次完成公共头部/导航/页脚、首页、分类、商品详情、搜索、购物车、账号、内容页、结账及订单页。

布局、图片裁切、字体、间距、轮播、悬停、抽屉和手机断点从基准提取为样式变量和可复用组件。保留 /collections/:slug 和 /products/:slug 等已知路径，迁移路径有明确重定向表。

先使用样本商品验证全部模板，再导入全量内容。交互读写新 API；服务器对金额、优惠和库存作最终校验。

验收：固定视口逐页截图对比，修复可见差异；另验证手机布局、长标题、缺货和空结果状态。

### 第五步：中文管理后台

| 模块 | 操作 |
| --- | --- |
| 商品 | 新增/编辑、上下架、搜索、批量操作、价格/原价、SKU、尺码、库存、SEO |
| 分类 | 层级、封面、排序、商品关联 |
| 媒体库 | 上传、预览、替换引用、排序、查看使用位置、处理未引用文件 |
| 首页 | 轮播、文案、链接、推荐分类/商品、模块排序、显示开关、预览后发布 |
| 内容 | 博客、常规页面、政策、导航、页脚 |
| 订单 | 查询、详情、支付/履约状态、发货和物流、受权限控制的退款 |
| 客户 | 客户与订阅列表、导出和必要的隐私权限 |
| 营销 | 优惠、免邮规则、活动有效期 |
| 设置 | 站名、Logo、币种、运费、邮件、客服、支付接口配置 |
| 系统 | 管理员角色、操作日志、导入报告和备份状态 |

一期使用受控首页模块，不做复杂的通用拖拽建站器。登录和权限服务端验证；上传验证类型/大小；密码安全哈希，登录限速，敏感操作有审计。

验收：后台修改一项商品和一个首页模块后，前台按预期更新；普通运营角色不能更改系统凭据。

### 第六步：交易及第三方服务

核实原站结账形式后实现新站订单流程。支付使用你自己的商户账户；先完成模拟/沙箱支付、金额核验、签名校验、回调幂等、超时和库存释放，再开启正式支付。邮件和客服同样使用你自己的配置。

免邮规则目前浏览器首页文案为购买三件及以上；适用地区、币种及例外仍需核对。订单中的优惠计算不能只信任浏览器提交值。

### 第七步：测试及验收

- 采集覆盖：唯一商品、分类关联、图片数量、失败资源、内部断链、残留原站服务调用。
- 视觉：固定桌面/手机视口逐模板对比，轮播和浮层状态另测。
- 管理：增改查、批量导入、上传、首页发布及权限隔离。
- 交易：规格/数量修改、服务器改价、库存不足、重复支付回调、取消、发货和退款状态。
- 部署：生产构建、健康检查、HTTPS、刷新路由、媒体持久化、备份恢复和回滚。

完成标准是可复现的验收报告；不以“首页看起来相似”代表完整商城完成。

### 第八步：部署到自己的服务器

1. 确认服务器系统、CPU/内存/磁盘、域名、现有站点及 Docker/面板环境。
2. 准备环境变量示例和初始化管理员方式，密钥单独注入。
3. 构建可固定版本的镜像，上传或通过镜像仓库分发。
4. 创建持久化数据库和媒体卷；先备份，再执行版本化迁移和数据导入。
5. Nginx 将商城、后台/API 和媒体分流，申请域名证书；后台可使用独立子域名。
6. 在测试域名验证站点、后台、图片、订单及沙箱支付。
7. 完成正式支付配置后切换正式域名，并检查 HTTPS、缓存和邮件。
8. 配置数据库与媒体的定期备份，备份存服务器外，执行一次恢复演练。
9. 交付更新步骤、迁移步骤、日志位置、备份恢复、上一版本镜像回滚方法。

资源需求在确认商品和媒体体积、访问量后评估。若是 Windows 或已有宝塔/1Panel，调整部署文件，不提前假定服务器条件。
