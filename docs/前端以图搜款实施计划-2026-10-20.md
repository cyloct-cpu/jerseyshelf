# 前端以图搜款实施计划

日期：2026-10-20。最新状态：2026-10-21按负责人明确授权先开放全部商品主图搜款，详情图在后台补齐，见 [正式上线记录](以图搜款正式上线记录-2026-10-21.md)。独立实拍和全面生产负载验收仍待后续进行；没有将试验成绩作为正式质量验收通过。试验阶段记录见 [预览使用说明](以图搜款预览使用说明-2026-10-20.md)。以下保留原完整实施计划。

## 1. 目标与现状

访客上传球衣图片、商品截图或实拍照片，在本站已上架商品中找到对应款式或相似款，点击后进入现有商品详情页。

现有前台顶部搜索框和 `/search` 页面均为文字搜索；查询由 `apps/api/catalog.mjs` 负责，页面由 `apps/storefront/views.mjs` 渲染。项目使用 Node.js 24、SQLite 和本地商品图库。历史采集规模为 4,166 件商品、约 35,000 张图片；实施时以生产库有效商品与图片关联为准重新统计。

检索范围只包含本站商品。返回结果是候选款式，不能保证仅凭照片识别准确赛季、球员版/球迷版、成人/儿童版或印字配置。

## 2. 前台入口和操作流程

1. 在截图中的顶部搜索框右侧增加相机图标，文字提示“以图搜款”，保留现有文字搜索按钮。桌面端和手机端都可打开。
2. 搜索页增加“文字搜索 / 以图搜款”切换入口，可直接选择图片、桌面拖拽或粘贴剪贴板图片。手机端通过系统选图器选择相册，设备支持时可拍照。
3. 显示图片预览，支持裁剪到单件球衣、重新选择和取消；提示“尽量保留球衣正面，裁掉聊天边框和无关背景”。只在用户点击“开始搜款”后上传。
4. 进入图片搜索结果页，保留查询缩略图和“更换图片”操作；默认按图片相似程度排序，每页最多 24 个商品，复用现有商品卡片、价格、语言和货币显示。
5. 图片结果可按分类、价格继续筛选。首版默认相似排序，价格排序作为明确的其他排序方式，不能筛选后退回整个商品库。文字查询切换回现有搜索；图片与文字联合检索留到后续。
6. 无可靠候选时显示“暂未找到足够相似的款式”，建议重新裁剪、换清晰照片或文字搜索。低匹配结果只作为“其他相似款”明确展示，不硬凑同款。

上传中、检索中、超时、图片无效、服务繁忙都给出可重试提示；图片搜索不可用时仍可使用文字搜索。入口、按钮和状态文案接入现有多语言流程。

结果采用“同款候选 / 相似款”等经过评估确定的文案，不将模型分数显示为“99%同款概率”。相似图片属于多个商品时可返回各自商品，供用户比较版本和尺码。

## 3. 推荐匹配方式

采用“图片特征检索 + 近重复图片辅助匹配”，先做效果试验再定型。

- 对商品关联图库提取视觉特征，建立图片到商品的索引。索引覆盖主图和有效正反面、细节图；不只搜主图。宣传图、尺码表和通用说明图应排除，现有图片角色先核查实际覆盖率。
- 对上传图片做方向校正、裁剪、缩放等一致预处理，再提取特征并查询相似商品图。查询与图库必须使用同一模型版本及预处理参数。
- 用图片哈希辅助找原图及近重复图；截图、换背景、实拍仍主要依靠视觉特征。哈希不能单独承担搜款。
- 先取图片候选，再按商品合并，采用最佳图片分数等规则排序，避免同一件商品因图库多而占满结果。按生产数据库重新过滤下架、删除及不可公开商品，并使用当前价格。
- 针对同队不同赛季、同配色不同款和正反面差异做单独评测。通用视觉模型未必能区分小标志与细节，不能提前承诺精确识别。

候选模型优先评估 Google SigLIP 2 Base 的视觉特征。其官方模型卡提供图像特征提取方式，标注 Apache-2.0 许可证；对本站球衣的匹配效果尚未实测。若尝试 ONNX Runtime Node.js 部署，需单独验证模型导出、算子兼容性及与原始模型的检索一致性；这不是已确认可直接运行的模型包。

## 4. 系统实现建议

流程：选图并裁剪 → Node 上传接口校验 → 独立图片检索进程提取特征 → 查询图库索引 → 商品合并与过滤 → 返回商品卡片。

网站主进程继续负责会话、校验和商品数据。模型放在独立工作进程或仅内网可访问的独立服务中，限制并发和线程，避免图片运算拖慢购物、下单。首版不在浏览器下载大模型。

建议先离线生成图库特征，并对约 35,000 张图片实测内存和检索时间。这个规模先比较内存矩阵检索与轻量近邻索引，无需一开始引入单独的向量数据库。内存不能只按索引估计，还需包括模型、图片解码及并发缓冲。

建议增加：

- `POST /api/image-search`：接收一张图片，返回短期查询编号和首批结果。
- 后续翻页/筛选接口：使用短期查询编号重新过滤同一候选集，服务器保存候选分数，不信任前端提交排名。
- 图片索引元数据：图片内容哈希、商品关联、模型版本、预处理版本、状态、失败原因、索引批次；向量文件单独存放，建立一致的版本清单。
- 后台维护入口：开关、已索引数量、覆盖商品数、待处理与失败任务、最近成功时间、手动重建及重试。初始默认关闭，通过验收后开放。

商品新增、换图、删除图和上下架都要触发增量同步。商品文字改动不必重算图片特征；模型升级需要重建对应版本。采用新索引生成、校验、原子切换，失败继续使用上一版；查询期间始终以当前商品状态过滤结果。

## 5. 上传处理与保留

首版一次一张，支持 JPEG、PNG、WebP，建议上限 8 MB、解码后 2,000 万像素。服务器验证实际格式、尺寸及可解码性，限制请求体、处理时间和并发；HEIC、动图等先给出明确格式提示。

图片重新编码并移除 EXIF；访客原图存放在非公开临时目录，处理后立即删除，失败残留由定时清理兜底。查询特征与候选集建议保留 30 分钟，过期提示重新上传；图片预览尽量使用浏览器本地对象 URL。结果页和日志不暴露原图路径，不长期收集访客照片，也不用于训练。页面说明临时图片用途。

按匿名会话与 IP 组合限流，设置全局队列上限及取消/超时机制。不接受任意远程图片网址，避免额外远程抓取风险。首次模型下载校验来源、版本和许可证；运行时不依赖临时在线下载。

## 6. 成本和部署选择

| 方案 | 优点 | 需评估的成本与限制 |
| --- | --- | --- |
| 现有服务器独立进程 | 不增加第三方按次识图费，查询图片留在本站 | 占用 CPU、内存；必须测试是否影响商城，现有余量尚未核查 |
| 单独检索服务器 | 可隔离资源并独立扩容 | 新增机器费用和运维；按压测确定配置 |
| 商业识图服务 | 可减少部分模型运维 | 需核对是否支持自建商品图库、地区可用性、按次费及图库费；上传第三方需另行明确 |

推荐先评估自托管方案。开源模型没有按次 API 费，但计算、存储和运维不是零成本。暂不购买服务器或调用收费接口；模型、硬件、工期和预算在试验后确定。

## 7. 分期实施与验收

| 阶段 | 工作 | 可审查交付 |
| --- | --- | --- |
| A：效果与资源试验 | 核对生产图库；建立有正确商品标注的测试集；比较候选模型、原图/裁剪图及哈希辅助效果；测 CPU、内存和耗时 | 匹配报告、失败样例、部署配置和预算建议；不先开放入口 |
| B：首版闭环 | 全量图库索引、上传与裁剪、相似结果、商品去重、筛选翻页、后台同步和错误提示 | 本地/预发布可操作版本，覆盖真实访客流程 |
| C：发布验收 | 索引备份、负载测试、多语言与手机检查、灰度开关、回滚演练 | 验收记录和线上可开关功能 |
| D：后续增强 | 按实测需求增加自动球衣定位、多件衣服选择、文字联合搜索、难例重排 | 单独评估收益和成本后安排 |

建议至少准备 120 个独立查询样本：原图及压缩/截图、裁剪/换背景、实拍/穿着、正反面差异、相似球队与赛季，以及库中不存在的款式。调参集与最终验收集分开，相同原图的多个变体不能同时跨两组造成成绩虚高。对多个商品共用图片的情况标注可接受商品集合。

首轮目标（作为是否继续开发的门槛建议，并非已达到）：

- 站内已有的清晰商品图和截图：正确款进入前 5 的比例目标至少 95%。
- 站内已有款式的实拍图：正确款进入前 10 的比例目标至少 80%，单独报告前排错款和困难样例。
- 无同款样本：不强行显示“同款”；分别统计错误强匹配和合理拒绝情况，确定阈值后冻结验收标准。
- 热服务、约定低并发下，提交后端到端 P95 目标不超过 5 秒；明确上传体积、并发、硬件和网络条件，冷启动单独统计。超限及时提示，不无限等待。
- 所有结果均为可公开商品，重复商品卡为零；新增/换图增量更新目标在 10 分钟内完成，下架商品立即从响应过滤。
- 服务中断、索引更新、畸形文件、超大图片、限流和恶意重复上传测试通过；同时验证商城文字搜索、商品页、购物车和结账可正常运行。
- 上线失败可关闭图片入口并切回上一索引/服务版本，不覆盖生产商品、客户及订单数据。

如果实拍效果或性能不达标，先给出失败分析及缩小范围/升级模型的选项，不以原图自匹配的成绩宣称功能完成。
