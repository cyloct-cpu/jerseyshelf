# WhatsApp 客户跟进与成交管理方案

日期：2026-10-15。状态：方案，尚未实施。用户明确以 WhatsApp 沟通和成交为主要业务流程，本方案调整《客户管理实施方案》的优先级，以留资、咨询、跟进、报价、收款和订单关联为主；账户与邮件订阅仍独立管理。

最新需求进一步明确邮箱注册、WhatsApp 联系核实、成交回访售后和网站直接下单首次联系四类场景，实施口径见 [客户四类场景与回访管理方案](客户四类场景与回访管理方案.md)。

## 1. 目标和现状

商家每天能直接看见：谁新来咨询、谁已报价、谁还没付款、谁今天需要跟进、谁已成交、谁明确不再购买。点击客户即可打开 WhatsApp、查看需求和历史跟进，成交后进入现有订单/发货流程。

当前网站只有注册/订阅名单、本地测试订单和匿名访问统计。商品描述的 WhatsApp 只是文字，未设置本店号码；尚无真实聊天入口、询价单、跟进任务、外部收款记录或 WhatsApp 消息回调。

推荐先实现“网站自动收集需求 + 后台管理跟进 + 商家在 WhatsApp 聊天 + 人工核实收款”，以后再评估官方 WhatsApp Business Platform 自动同步。当前不注册账号、不购买服务、不部署服务器、不发送消息。

## 2. 顾客流程

### 商品咨询

商品页增加“WhatsApp 咨询 / 下单”，先保留顾客所选 SKU、尺码、数量、印字、臂章及展示币种。打开简短表单：

- 必填：国家区号与 WhatsApp 号码。
- 选填：称呼、所在国家/地区、咨询内容。
- 清楚说明资料用于回复此次咨询，营销订阅另行选择，不默认勾选。

提交成功后，服务器先保存咨询，再显示“前往 WhatsApp”，生成带随机咨询编号的预填消息。页面先提供编号和复制按钮，避免弹窗被拦截导致记录和跳转丢失。顾客可修改并须自行发送消息。

示例预填文本（按顾客所选前台语言生成公共提示语，印字原文不外送翻译）：

```text
Hello, I would like to ask about enquiry Q-7K9P2M.
Product: 2026-27 Bayern Munich Away — Fan Edition
Size: L | Quantity: 2
Printing: [customer selection]
Patch: [customer selection]
Please confirm the total and delivery cost.
```

编号只用于人工对应，不是订单读取凭据；不能凭编号下载其他客户资料。预填 URL 不放完整地址、邮箱或收款凭证。商家收到后按编号找到咨询，核对号码并记录联系结果。若客户删除编号，可用号码和商品核对，冲突由人工确认。

### 多件商品

购物车增加“通过 WhatsApp 确认订单”，保存整个商品清单与定制快照，再生成咨询编号。长清单留在后台，预填消息只带编号、件数和简要摘要，避免链接过长。

### 已下单、未付款

未来实际使用时，顾客可提交正式“待付款订单”，随后通过 WhatsApp 确认和收款。已存在订单时只关联，不再次创建。当前模拟付款流程不能直接冒充正式成交，须新增外部收款流程并区别测试数据。

### 纯聊天/站外客户

顾客直接添加 WhatsApp、未填写网站表单时，商家在后台手动新增联系人/咨询，输入号码、来源和需求。网站不能凭匿名访问或点击推断真实号码。

为减少流失可保留“直接咨询、不留资料”入口，但这一类只统计匿名点击，无法保证知道是谁或主动联系。若业务目标是每次都可跟进，主入口应要求先填号码，表单只保留必要字段。

## 3. 一位客户可以有多张咨询单

客户档案记录联系人；咨询单记录本次购买机会。一个老客户买过一次，下一次咨询仍可能未成交，因此不能仅给客户设置一个“已成交/未成交”状态。

建议结构：一个客户 → 多张咨询单 → 报价记录、跟进任务 → 一个或多个关联订单。客户详情同时显示历史成交与当前待跟进咨询。

## 4. 状态设计

### 咨询/销售阶段

| 阶段 | 含义与进入方式 |
| --- | --- |
| 新咨询 | 网站留资成功或后台手工建立，尚未确认真实聊天 |
| 已联系 | 商家实际完成联系并手工记录；第一版不能仅凭按钮点击自动判断 |
| 已报价 | 保存报价、币种、运费与有效期；商家记录是否已告知客户 |
| 考虑中 | 客户在比较、等待决定，填写下一次跟进时间 |
| 待付款 | 客户确认购买，已关联待付款订单 |
| 已成交 | 关联订单已完成收款核实；定金未收齐时单独显示，默认不算全额成交 |
| 暂缓 | 客户表示稍后购买，设置预约跟进日期 |
| 已流失 | 明确不购买或人工结案，选择原因；可重新开启 |

长时间没回复先进入“需要跟进/已逾期”，不自动认定流失。流失原因可选价格、运费、尺码缺货、配送时间、暂不需要、联系不上、其他。

### 订单的独立状态

付款：未付款、部分收款、已收齐、已退款/部分退款。发货：待处理、已发货、已完成/已取消，按实际已实现与后续扩展区分。

“客户说已付款”“上传凭证”“商家核实到账”是不同事件。人工核实到账时记录金额、币种、收款时间、方式、参考号与操作者；不能凭聊天、截图或 WhatsApp 的送达/已读直接标记收款成功。

## 5. 后台布局

导航建议将“客户与订阅”扩展为“客户与跟进”，订阅保留单独子页。

### 工作台

优先入口：今日待跟进、已逾期、新咨询、已报价未成交、待付款、已成交、已流失。支持列表和按阶段分栏看板，第一版以可搜索筛选的列表为主。

列表列：称呼、WhatsApp 号码、国家/语言、咨询编号、意向商品、阶段、意向/报价金额、上次实际联系时间、下次跟进时间、负责人、关联订单、操作。

快捷操作：打开 WhatsApp、复制预填话术、记录跟进、设置提醒、保存报价、关联/创建待付款订单、核实收款、暂缓/结案。打开聊天只记录“打开聊天入口”，实际联系/发送仍由人确认。

### 客户详情

- 基本信息及来源：网站商品页、购物车、广告参数（有来源数据时）、手动录入、老客。
- 当前咨询与历史咨询、商品规格/定制快照。
- 报价版本、运费、折扣、币种、有效期。
- 跟进时间线：沟通摘要、客户反馈、阶段变化、操作者。
- 下次待办：时间、负责人、目的；完成后要求选择是否建立下一次待办。
- 成交订单及收款记录、收货和物流信息。
- 标签：新客、复购、批发、重点意向等；客户提出不再联系时记录并停止普通跟进提醒，必要的订单服务另行处理。

后台备注与客户资料不进入公共翻译队列，报价及订单资料不放在无需鉴权的公共页面。

## 6. 跟进方式

系统生成后台待办，按下一次跟进时间排序，并显示逾期天数。建议提供可修改的默认间隔：首次报价后 1 天、后续 3 天/7 天、待付款 1 天；仅作为内部提醒，尊重客户约定时间和当地时区。

每天流程：打开今日待跟进 → 进入咨询 → 查看商品和上一条备注 → 点击 WhatsApp 沟通 → 回后台记录实际联系和结果 → 更新阶段 → 设置下一次日期。未完成待办持续显示；无联系方式的记录单独标记为不可主动联系。

话术可按客户语言准备“确认尺码、报价、付款提醒、发货通知、回访”等模板；第一版只复制或预填，商家审核并手工发送。不自动群发，不自动读取 WhatsApp 私聊。

## 7. 成交、报价和订单关联

先保存询价和报价，不锁库存、不计成交。客户确认后创建/关联正式待付款订单，复用现有价格、定制、折扣、货币快照和库存校验。正式订单的占库存及取消恢复规则单独确定并在页面说明，避免未付款报价长期占用库存。

在 WhatsApp 谈妥的价格可能与网站价格不同，报价应保存商品金额、定制费用、运费、折扣、总金额和币种；客户确认时冻结报价版本。正式订单不能只加备注而仍按错误总额计费。订单/收款创建使用幂等处理，重复点击不重复建单或重复计款。

付款核实后更新收款账目，订单满足全额结清条件才标记已成交；取消和退款保留流水，不删除历史。不同币种不能直接相加；跨币种统计使用当时冻结的基准金额，并明确人工录入收款与线上支付回调的来源。

当前订单系统没有正式外部收款状态，实施时必须扩展，不能把 `test_paid` 当作真实付款。

## 8. 号码、去重与归属

以带国家区号的规范化 WhatsApp 号码作为主要联系匹配线索，保留原输入及来源，不仅按姓名合并。网站表单填写的号码标记为未核实；聊天实际号码核对后记录验证来源。

同一号码重复咨询尽量关联联系人，但新的购买需求保留新咨询，网络重试则用提交标识去重。同一客户多号码、多人共用号码和矛盾资料进入人工核对，不自动合并账户或赋予历史订单访问权限。

销售跟进记录以客户/咨询归属为核心，现有登录账户的订单授权继续独立执行。仅有号码或咨询编号不能自动登录或查看私密订单。

## 9. 自动化边界和后续官方接口

第一阶段普通点击聊天链接只能打开聊天并预填文本，客户仍须发送；网站只知道自身表单和点击事件，不能由此确认 WhatsApp 消息已发送、已回复或已付款。官方点击聊天说明：https://faq.whatsapp.com/5913398998672934 。

未来若需要自动记录收到的消息、识别发送方和消息送达状态，可评估 WhatsApp Business Platform Cloud API 和 Webhook。仅同步已接入通道实际收到的事件，不承诺取得个人账号全部聊天历史；送达/已读事件也不是付款事件。官方事件参考：https://www.postman.com/meta/whatsapp-business-platform/folder/tduohwq/webhook-payload-reference 。

正式接口需要相应业务账号/号码配置和公网可验证 HTTPS Webhook；实际接入要核对现有号码的适用方式和权限。平台存在按消息类别、接收市场计费的规则，不能承诺全免费或任意自动追发。费用及消息窗口以官方说明为准：https://business.whatsapp.com/products/platform-pricing 。本阶段不开户、不发送、不承担平台费用。

## 10. 实施顺序

1. 建立客户、咨询、需求快照、阶段历史、跟进任务和联系方式结构；保留现有账户/订单权限。
2. 后台完成客户/咨询列表、详情、筛选、备注、阶段变更、今日和逾期待办、手工录入客户及打开 WhatsApp。
3. 商品页、购物车添加留资和咨询入口；商家号码后台配置；保存咨询成功后生成编号和预填消息。
4. 建立报价版本、正式待付款订单关联及人工收款核实；测试与真实数据分开，验收库存、金额和退款处理。
5. 增加有效线索数、实际联系数、报价数、待付款订单数、已成交咨询数、未成交原因与跟进完成情况。转化率使用明确同一批次/时间范围的咨询口径；匿名点击单独统计。
6. 客户量增加后再决定是否接官方消息 API、多客服分配或更细权限。

源代码按客户、咨询、跟进、报价/收款和后台页面分模块；数据库使用下一个空闲版本的迁移文件，不直接堆到 `views.mjs` 或 `server.mjs`。实施前备份，新增业务用隔离测试数据验收，不向真实客户发送测试消息。

实施时需商家提供本店 WhatsApp 号码（含国家区号），并确定是否保留网站普通下单、收款方式和成交确认口径；可先做不依赖这些信息的后台与数据结构。当前只完成方案。
