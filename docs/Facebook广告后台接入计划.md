# Facebook 广告后台接入计划

日期：2026-10-17。状态：方案阶段，尚未开发、连接广告账户或发布广告。

## 1. 目标与推荐范围

在现有中文后台新增“Facebook 广告”模块，串起广告计划、Meta 账户数据、网站访问、订单和真实收款，让运营能看清“哪条广告带来访问、订单和到账”。

建议分期完成：第一期做本地广告计划、账户连接与报表同步；第二期做网站归因、Meta Pixel 和 Conversions API（CAPI）转化回传；第三期才做后台创建、发布和调整真实广告。第一、二期可继续在 Meta Ads Manager 中投放，本后台负责管理计划、查看数据和回传转化。

“本地广告计划”是运营草稿；Meta 的广告系列（Campaign）、广告组（Ad Set）、广告（Ad）为三个不同层级。保存本地计划不会自动创建平台对象；平台发布状态、审核状态和实际投放状态分别展示。

## 2. 与现有项目的衔接

| 现有位置 | 已有能力 | 计划接入点 |
| --- | --- | --- |
| `apps/api/server.mjs` | Node HTTP 路由、会话及 CSRF | 增加后台路由和有限的前台事件入口 |
| `apps/admin/views.mjs` | 中文后台导航、通用页面壳 | 增加“Facebook 广告”导航 |
| `apps/api/db.mjs`、`database/migrations/` | SQLite、事务、迁移、设置、审计 | 新增广告表及配置，不改现有订单含义 |
| `apps/api/traffic.mjs` | 访问统计及访客标识 | 增加独立来源关联；现有访问统计不等于广告追踪许可 |
| `apps/api/orders.mjs` | 下单、测试与正式订单分流 | 下单时固化订单来源快照 |
| `apps/api/customer-payments.mjs` | 正式订单人工核实收款与退款 | 首次全额到账时生成 Purchase 待回传任务 |
| `apps/api/whatsapp-config.mjs` | 服务端加密配置的已有实现 | 参考其模式建立独立广告凭据存储 |
| `scripts/ops/backup.mjs` | 数据库、媒体及接口密钥备份 | 增加广告凭据密钥的备份和成套恢复说明 |

继续使用现有 Node HTTP、服务端页面和 SQLite；通过服务端 HTTP 调用 Meta API。首版单店铺、单广告账户，表结构预留多账户。

## 3. 后台页面与操作

建议入口：`/admin/facebook`，下设以下页面。

| 页面 | 主要内容 |
| --- | --- |
| 广告概览 | 花费、曝光、链接点击、网站来源访问、下单数、实收订单数；显示币种、报表日期及更新时间 |
| 广告计划 | 新增、编辑、复制、归档计划；维护商品/分类、目标市场、语言、素材、落地页、预算和投放时间 |
| 平台广告 | 展示 Campaign → Ad Set → Ad，绑定本地计划，查看平台状态；首期只读 |
| 效果报表 | 按日期、计划、系列、广告组、广告查看平台数据及本地订单归因 |
| 转化事件 | 第二期提供：测试/正式事件、队列状态、失败原因、重试、去重与订单关联 |
| 账户与设置 | 账户 ID、API 版本、凭据、Pixel/数据集 ID、连接检查、同步时间及关闭开关 |

计划字段：名称、负责人、目标、国家/地区、语言、商品或分类、落地页、素材及文案、建议受众与版位、预算类型（日/总额）、预算币种、开始/结束时间、状态、备注、平台对象关联。可先保存不完整草稿；标记“待投放”前校验必填项。第一期的受众与版位只是计划内容，不代表平台已接受。

计划状态建议：草稿 → 待投放 → 投放中 → 已暂停 → 已结束/归档。手工运营状态与平台同步状态并排展示；关联 ID 只能绑定到当前账户中读取到的对象。

计划支持生成带来源参数的链接，使用稳定 ID：`utm_source=facebook`、`utm_medium=paid_social`、`utm_campaign=<本地计划ID>`；第三期发布时再加入平台支持的广告系列/组/广告 ID 动态参数，具体语法实施时核对。Instagram 来源保留实际平台值，不强行全部标为 Facebook。

## 4. 账户、凭据和外部准备

本地计划管理无需 Meta 凭据。实际同步前需要商家提供或完成：

1. 可管理的 Meta 业务资产、广告账户和有权访问该账户的开发者应用/访问令牌。
2. 账户读取与报表所需权限，计划从 `ads_read` 核对；第三期写入再核对 `ads_management`。是否需要额外资产权限、应用审核、访问级别或企业验证，以实际账户和应用用途核实，不能仅凭填写 Token 判断可用。
3. 第二期需要 Pixel/数据集及其 CAPI 凭据；广告读取 Token 与 CAPI Token 分开管理和验证，不假定一个 Token 可完成全部操作。
4. 第三期需要可用于广告的 Facebook 公共主页；若投放 Instagram，再准备对应身份资产。素材、落地页、商品可售性及广告账户支付方式由商家核对。
5. 正式网站的 HTTPS 域名、可访问落地页和追踪说明；域名验证及其他资产设置按 Meta 当前要求完成。本轮不包含服务器部署。

Graph API 版本实施时选择受支持版本并固定保存，不预填猜测的“最新版本”。后台连接检查分别记录令牌可用、账户归属、广告读取、报表读取、数据集事件测试等结果。

凭据在服务端加密保存，采用独立的 `facebook-ads-credentials.key`，不与 WhatsApp 共用令牌或加密文件；页面只显示是否配置与检查状态。凭据不进入页面源码、导出和普通日志。更换账户或凭据后使旧的检查结果失效。

## 5. 网站来源与订单归因（第二期）

流程：广告点击 → 落地页来源参数 → 经许可的访问来源记录 → 加购/结账 → 订单来源快照 → 实收关联 → 本地报表及转化回传。

- 保存合法且限长的 UTM、平台对象 ID、落地页路径和时间；`fbclid`、`_fbc`、`_fbp` 按 Meta 参数规范及追踪许可处理，缺失时留空，不伪造。
- 推荐本地默认展示“30 天内最后一次可识别的广告点击”，同时保留首次来源；窗口可配置，明确这是本地规则，参数本身不证明平台归因。实施前确认该默认规则。
- 参数是外部输入；只作来源线索，不允许修改订单价格、访问权限或收款状态。无来源的订单显示未知/直接来源，不猜测为 Facebook。
- 订单创建时保存独立快照，后续会话变化不覆盖；跨设备且无法可靠关联时保持未知，不宣称全部订单都能归因。
- 现有 WhatsApp 联系许可和邮件订阅不能作为广告追踪许可；增加独立广告追踪选择、许可版本及时间。未取得所需许可时不加载广告 Pixel、不进行相应广告追踪或 CAPI 发送；撤回后停止并取消未发送任务。哈希后的个人数据仍按个人数据处理。
- 第一、二期不上传现有客户名单、不创建客户名单受众，不把全量客户历史发给 Meta。

## 6. Pixel 与 CAPI 事件规则（第二期）

| 事件 | 业务触发点 | 首版发送方式 |
| --- | --- | --- |
| PageView | 用户实际访问前台页面 | 获得所需许可后浏览器 Pixel |
| ViewContent | 有效商品详情展示 | 浏览器 Pixel；商品 ID 与后续目录保持统一 |
| AddToCart | 服务端确认成功加购 | 浏览器 Pixel；刷新、失败点击不重复计事件 |
| InitiateCheckout | 有效购物车进入结账 | 浏览器 Pixel；按结账尝试去重 |
| Purchase | 正式订单首次核实全额到账 | 服务端 CAPI，不依赖用户再次打开订单页 |

关键约束：

1. Purchase 只针对 `order_kind='external'`、首次由非全额到账进入 `payment_status='paid'` 且符合发送条件的订单。测试单、`test_paid`、下单成功、部分收款、重复登记都不触发购买转化。
2. 稳定使用 `purchase:<订单ID>` 等事件 ID；同一事件的重试不更换 ID。退款后再收齐款不为同一订单再次生成 Purchase。今后若补充浏览器 Purchase，必须与服务端使用同一事件名和事件 ID 去重，不能在订单页刷新时新建购买事件。
3. 与收款事务同时持久化事件任务，事务提交后异步发送；Meta 异常不回滚真实收款或阻塞结账。重复执行收款请求不重复排队。
4. 使用实际发生时间，不以重试时间伪装新事件。人工晚登记、延迟付款和队列积压需按实施时官方的事件时限及 action_source 规则处理；超出可接收范围显示“不可回传”，不篡改时间。人工收款可能对应网站、聊天或线下成交，不能一律标为 website。
5. 金额使用订单实际结算币种及其小数位，由最小货币单位准确转换；首版 Purchase value 定义为含运费、扣优惠后的订单总额，并在后台注明。禁止把分/厘直接当主币单位，禁止固定全部为 USD。
6. 邮箱/电话按当时 Meta 规范标准化、哈希；点击/浏览器标识按官方要求传递，不统一哈希。只发送事件必需数据，地址、订单备注、聊天内容不进入广告事件。来源 URL 去除订单访问密钥及敏感查询参数。
7. 退款进入本地净收入与 ROI 报表；不发送负数 Purchase，也不承诺退款会自动撤销 Meta 已统计的转化。退货/退款的额外平台处理后续核对。

参考依据：Meta [官方 SDK 事件定义](https://github.com/facebook/facebook-python-business-sdk/blob/main/facebook_business/adobjects/serverside/event.py)包含事件时间、来源与身份字段，并说明事件名和事件 ID 用于识别浏览器与服务端相同事件。本文规定的支付触发点、金额范围和本地归因窗口是本项目设计决定。

## 7. 报表、同步和可靠性

平台报表读取花费、曝光、链接点击及选定的转化类型和金额；平台与本地各自展示购买数和 ROAS，禁止混算。CPC 的点击口径固定为链接点击；CTR 使用同一口径。Meta 转化需保存选定 action_type 和归因设置，不把所有 actions 相加当购买数。

本地另展示归因下单数、已全额到账订单数、净实收和退款。若计算“本地净实收/广告花费”，明确名称与归因窗口；币种不同时须有可追溯汇率，未换算时不出比值。零点击、零购买或零花费时显示“—”。无成本数据时不把 ROAS 称为利润。

建议每小时同步平台对象及当日报表，每天回补最近 7 天，支持按日期人工重拉；这只是初始调度设计，平台归因可能更晚修正，需要允许扩大回补窗口。按账户时区读取和展示平台日报，保留时区及币种；本地现有访问统计按北京时间，未对齐时不直接拼接日报。

同步任务需处理游标分页、分批请求、任务锁、超时及进程重启恢复；数据按账户/对象/日期/报表口径唯一键更新。429、可恢复网络错误和部分 5xx 退避重试；权限、令牌失效或参数错误停止自动重试并提示处理。大报表按官方支持的异步查询机制实现。失败保留上次成功数据并标注过期，不显示假零。

事件队列至少包含待发送、处理中、平台已接受、待重试、失败、取消、不可回传；记录尝试次数、下次时间及脱敏错误。使用租约恢复中断任务，同一任务重试保留事件 ID。平台接受不等于已归因到广告或报表已更新。

| 路由 | 用途 |
| --- | --- |
| `GET /admin/facebook` | 概览 |
| `GET/POST /admin/facebook/plans` | 列表、新建计划 |
| `GET/POST /admin/facebook/plans/:id` | 查看、修改计划，版本冲突保护 |

## 9. 分期实施和验收

### 第一期：计划管理与只读数据接入

交付导航与页面、计划增改复制归档、账户凭据和检查、平台对象读取绑定、基础日报、同步任务及备份说明。

验收：无 Meta 凭据也可管理本地计划；有效账号能分页读到真实广告及报表；重复同步不重复累计；令牌失效明确报错；时区与币种可见；所有写操作具备后台权限与 CSRF；连接检查和同步不创建广告、不改变预算。

### 第二期：来源关联和真实转化

交付独立追踪许可、来源快照、Pixel、Purchase CAPI 队列、测试模式、失败重试及本地到账报表。先用隔离的测试数据验证，再配置正式数据集；测试事件不得混入正式统计。

验收：测试单、未付款单、部分收款不产生正式 Purchase；正式订单首次全额到账只排一次，退款后再次到账仍不重复；两次有效加购能区别于重复提交；拒绝/撤回追踪时不继续发送；双端事件 ID 一致；不同小数位币种正确；超时、重复任务和进程重启可恢复；Meta Events Manager 实测收到并核对事件，不能只依赖本地“成功”。

### 第三期：后台投放操作

在账户具备写权限后增加 Campaign/Ad Set/Ad 创建、素材上传、预算修改和暂停/恢复。先生成平台暂停状态对象，提供完整预览，明确账户、对象、金额币种、日预算/总预算、排期时区、身份资产、素材及落地页。实际启用由运营明确执行；保存草稿不启用投放。

发布采用请求去重、版本校验、远端结果核对及审计；处理三层对象部分创建成功、响应丢失和重复点击，避免重复建广告或误启用。平台审核通过、有效状态及实际投放结果必须回读，不能以 API 接受请求代替投放成功。

第三期验收：创建对象默认暂停；预览内容与远端一致；重复提交不重复建对象；预算及启停结果能回读；权限不足或对象过期时阻止写入；失败明确指出哪些对象已创建。

实施时增加相应单元/HTTP 集成测试，覆盖以上业务边界；回归现有订单、收款、客户、访问统计和 WhatsApp。外部联调和正式投放验收单列，不把 mock 测试视作已连通 Meta。

## 10. 实施前待确定项与默认建议

- 首版范围：建议第一期先落地，再做第二期；第三期单独排期。
- 首个广告账户、Pixel/数据集、正式域名：待提供，均不影响先开发本地计划功能。
- 投放国家、语言、主推商品、日预算和币种：由运营填写，计划先支持空白草稿，不擅自指定金额。
- 本地归因：建议最后一次广告点击 30 天，并保存首次来源；与 Meta 平台归因分开显示。
- 事件数据保留：建议可识别来源和事件明细默认 90 天，聚合报表另定；实施前按业务需求及适用要求确认，避免无期限保存。
